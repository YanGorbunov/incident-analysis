# Ретроспектива: ВКР через два года

**Проект:** компонент учёта и анализа инцидентов системы управления инцидентами ГС ПВДНП
(ВКР, РТУ МИРЭА, 2024; только проектирование).
**Сейчас:** реализация «как в дипломе, но правильнее» после двух лет коммерческой разработки на Java.

Этот документ — честный разбор: что в проекте было сделано хорошо, где он расходился сам с собой,
что я изменил при реализации и почему. Ссылки вида «Рис. 3.4», «Табл. 2.3» — на текст ВКР.

---

## 1. Что в ВКР было хорошо и сохранено

- **Сквозная логика.** AS-IS → проблемы → требования → TO-BE → модели → интерфейс.
  Каждое решение в коде по-прежнему отвечает на проблему из п. 1.2: ручной перенос данных,
  ручная категоризация, ручные отчёты.
- **Предметная модель.** Набор сущностей (инцидент, КЕ, ведомство, ПО, справочники) выбран верно;
  менять пришлось связи и типы, а не саму модель.
- **Справочники и система кодирования** (Табл. 2.3–2.7) — перенесены почти дословно, включая
  описания приоритетов и статусов.
- **Экранные формы** (Рис. 3.5–3.13) — интерфейс повторяет макеты: оранжевая плашка пользователя,
  меню слева, импорт по ID над списком, параметры категории, сводный отчёт с круговой диаграммой.
- **Формулы** 2.1 (процент закрытых) и 2.2 (среднее время разрешения) реализованы и покрыты
  тестом на известных числах (`CategoryReportIT`).

## 2. Где проект расходился сам с собой

Это не ошибки защиты, а то, что всплывает в момент, когда по проекту начинаешь писать код.

| # | В ВКР | Проблема | Как сделано |
|---|-------|----------|-------------|
| 1 | Категория = `(id, name, creation_date_time)` | Центральная идея — категория как набор параметров фильтра (Рис. 3.12) — в схему не попала. Категорию нельзя было бы пересчитать или понять, по какому правилу она выделена | `category.criteria JSONB` — сам фильтр; `category_incident` — зафиксированный срез. См. [ADR-0002](adr/0002-category-filter-and-snapshot.md) |
| 2 | Коды `ГГММДД.XXXX`, `ВВВ.XXXX`… как «формулы идентификатора», ключи `BIGINT` | Код с точкой не помещается в BIGINT; формат кода инцидента назван ГГММДД, но описан и нарисован как ДДММГГ; пример «30 марта → 300224» ошибочен (это 30.02) | Суррогатный ключ + отдельный неизменяемый бизнес-код. Формат ГГММДД (сортируется). Номер за сутки — атомарный счётчик. [ADR-0004](adr/0004-business-codes.md) |
| 3 | Должность `ОО.XX` кодируется кодом отдела | Внешнего ключа `post → department` нет, зато у сотрудника есть и `post_id`, и `department_id` (нарушение 3НФ, возможна рассинхронизация) | `post.department_id NOT NULL`, у сотрудника только должность |
| 4 | Сотрудник = пользователь: логин и пароль у каждого ответственного | Ответственные приходят из трекера и в систему не входят; входят аналитики | `employee` (ответственный) отдельно от `app_user` (учётная запись), связь 0..1 |
| 5 | `password VARCHAR(45)` | Хэш bcrypt — 60 символов; по размеру поле подходит только для открытого текста | `password_hash` с префиксом алгоритма (`{bcrypt}…`), DelegatingPasswordEncoder |
| 6 | `description VARCHAR(255)` | По тексту туда попадают лог-файлы и системные журналы | `TEXT` + полнотекстовый индекс (морфология русского) |
| 7 | `CHECK (registration_date_time <= NOW())` | Недетерминированная функция в CHECK: проверяется только при записи, а восстановление дампа через год упадёт или пройдёт — по случайности | Проверка в приложении с допуском на рассинхронизацию часов |
| 8 | `ip_address VARCHAR(20)` | Нет проверки формата, IPv6 не помещается | `INET` |
| 9 | Описание у статусов/приоритетов есть в справочниках (Табл. 2.6–2.7) и на макете (Рис. 3.8) | В физической модели колонки нет | Добавлено |
| 10 | Формула 2.2 по всем N инцидентам | У незакрытого инцидента нет T закрытия | Среднее по закрытым; это явно указано в отчёте |
| 11 | «Только ANSI SQL ради переносимости» | Ради гипотетической миграции отказ от того, что делает PostgreSQL выбором: FTS, JSONB, INET, `percentile_cont`, `FILTER` | Используются возможности PostgreSQL; миграция на другую СУБД в реальности не планировалась ни разу |

## 3. Что было заявлено, но не спроектировано

| Требование ВКР | Было | Стало |
|----------------|------|-------|
| Интеграция с системой управления задачами (Табл. 1.2) — ключевое | Одна фраза: «импорт путём введения идентификатора» | Порт `TaskTrackerClient`, две реализации (тестовые данные / REST), маппинг статусов и приоритетов в конфигурации, идемпотентный upsert по `external_id`, автоимпорт недостающих КЕ, предупреждения вместо падений, журнал импортов в отдельной транзакции, метрика `incidents.import` |
| SLA (упоминается в п. 1.2 десяток раз) | Ни одного атрибута | Целевые сроки реакции и решения у приоритета; моменты реакции/решения/закрытия у инцидента; % соблюдения в отчёте и фильтр «нарушен SLA» |
| Двухфакторная аутентификация (п. 3.4) | Упомянута | TOTP (RFC 6238) без внешних библиотек, проверено тестовыми векторами RFC |
| Журнал событий (п. 3.4) | Упомянут | `audit_event`: входы, неудачные попытки, блокировки, все изменения данных; пишется в той же транзакции |
| Пароль «высокой сложности» | Без критериев | ≥ 12 символов, без логина (NIST SP 800-63B: длина важнее спецсимволов), блокировка после 5 неудач на 15 минут |
| «Модуль резервного копирования» (Рис. 3.3) | Модуль приложения | Задача инфраструктуры: `pg_dump` по расписанию с ротацией в docker-compose и скрипт восстановления. [ADR-0005](adr/0005-backups-are-infrastructure.md) |
| Разграничение прав по принципу наименьших привилегий | Один пользователь — аналитик | Роли ADMIN / ANALYST / VIEWER: статусы и приоритеты влияют на аналитику, поэтому их меняет только администратор |

## 4. Аналитика: что добавлено и зачем

В ВКР два показателя — процент закрытых и среднее время разрешения. Для отчёта руководителю этого
мало, а среднее ещё и вводит в заблуждение.

- **Медиана и 90-й перцентиль.** Время решения распределено с длинным хвостом: один инцидент,
  провисевший месяц, сдвигает среднее сильнее, чем двадцать решённых за час. Медиана отвечает на
  вопрос «как обычно», p90 — «сколько ждать в худшем разумном случае».
- **Время реакции** — первый переход в рабочую фазу. Берётся из смены статуса, а не вводится руками.
- **Соблюдение SLA** реакции и решения. SLA решения считается до «Решён», а не до «Закрыт»:
  ожидание подтверждения от пользователя — не вина исполнителя.
- **Фазы статусов** (`NEW / ACTIVE / RESOLVED / CLOSED`). Аналитика опирается на фазу, а не на
  название, поэтому переименование статуса или новый статус ничего не ломают.
- **Разрезы:** по ведомствам, по КЕ (что ломается чаще всего — главный вопрос анализа инцидентов,
  которого в ВКР не было), по ответственным, понедельная динамика «зарегистрировано / закрыто».
- **Воспроизводимость.** Отчёт строится по зафиксированному срезу в одной транзакции
  `REPEATABLE READ`: цифры в шапке и в таблице согласованы, а отправленный руководителю отчёт не
  «уплывёт» через неделю.
- **XLSX — с числами, а не с текстом**, и с нативной диаграммой Excel, чтобы аналитик мог считать
  дальше. DOCX — по макету Рис. 2.6.

## 5. Технические решения

| Решение | Почему |
|---------|--------|
| Spring Boot 4, Java 25, Gradle | Актуальная LTS-платформа; мой рабочий стек |
| `JdbcClient` + SQL вместо JPA | Модель простая, а аналитика — это SQL с `FILTER`, `percentile_cont`, FTS. ORM здесь добавил бы слой, который в отчётах всё равно обходят. [ADR-0001](adr/0001-jdbc-client-over-jpa.md) |
| Сессия + CSRF-cookie вместо JWT | Один сервер, один клиент на том же origin. Сессию можно отозвать, токен в `localStorage` — мишень для XSS. [ADR-0003](adr/0003-session-auth-for-spa.md) |
| Оптимистичная блокировка (`version`) | Два аналитика правят один инцидент — второй получит 409, а не молча затрёт изменения |
| Flyway, демо-данные отдельной локацией | Схема воспроизводима; демо-данные не попадают в боевую базу |
| Testcontainers с настоящим PostgreSQL | FTS, INET, JSONB и перцентили в H2 не проверить |
| Один jar с фронтендом внутри | Проще развёртывание; SPA и API на одном origin |
| Первый админ из переменных окружения | Хэш пароля в SQL-миграции — это пароль в репозитории |

## 6. Чего сознательно не делал

- **Kafka, микросервисы, Kubernetes.** Нагрузка — десятки инцидентов в день, пользователей — единицы.
- **Вебхуки из трекера.** В ВКР импорт инициирует аналитик, и это осознанное решение: не всё из
  трекера является инцидентом для анализа.
- **Своя реализация QR-кода для TOTP.** Секрет показывается текстом и ссылкой `otpauth://`.
- **PDF-экспорт.** Требование ВКР — DOCX и XLSX.

## 7. Уроки

1. **Проектирование без кода не замечает противоречий.** Почти все пункты раздела 2 видны только
   при попытке написать `INSERT`. Даже скелет кода на этапе проектирования окупился бы.
2. **Главная идея должна дожить до схемы данных.** Категория как фильтр — суть компонента, и именно
   она потерялась между логической и физической моделью.
3. **«Интеграция» — это не требование, пока нет контракта.** Маппинг полей, идемпотентность,
   поведение при частичных данных — это и есть интеграция.
4. **Метрики требуют модели времени.** Чтобы считать SLA, нужно хранить моменты реакции и решения
   и выводить их из переходов статусов, а не просить человека заполнять.
5. **Раздел безопасности должен ссылаться на схему.** Требование «высокая сложность пароля» рядом с
   `VARCHAR(45)` — сигнал, что разделы писались независимо.
6. **Переносимость ради переносимости дорого стоит.** Выбрал PostgreSQL — пользуйся PostgreSQL.
